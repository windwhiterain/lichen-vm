# 让任意属性像类型一样参与类型检查 —— lichen 的可扩展属性系统

> 本文假设读者已了解 lichen 语言本身:`[value, type]` 递归 pair、单宇宙 `Type : Type`、依赖类型(数组长度 pinning)、数组/元组/结构体/表、惰性 + 统一运行时、块级 GC、以及"类型即值 / 运行时即类型检查器"的哲学。这里不再展开那些细节,只聚焦一件事:
>
> **如何把"一个(几乎任意的)属性"纳入类型系统,并且让它享受与"类型"完全同一套机制 —— 同一个 pair、同一个统一、同一个惰性、同一个检查即运行。**

---

## 1. 问题: 类型之外,还有一维要管

GPU 编程里,除了"这个值是什么类型",程序还要知道"这个值在哪些线程上是均匀的"。论文 _Modular GPU Programming with Typed Perspectives_ 把后者编码成了类型层面的一个**第二个属性**:一个数据要么在 `thread[1]`、`thread[4]`、`block[1]`……上均匀(即按某个粒度分组,组内线程看到相同的值)。

lichen 没有 GPU,但它想证明的不是"Perspective 这一个特例",而是**机制**:一个语言里,如果每个表达式已经带着一等的 `[value, type]` pair,那么它也应该能携带**额外的、可选的属性**,其**格(lattice)、序、闭包不是写死在核心里的**，而是由可插拔的**扩展**提供。Perspective 只是第一个实例;未来的 GPU DSL 前端、生命周期、效应、或 staging 级别都能以同样的方式接入。

**关键观察**:lichen 的"类型即值"是**递归可复用的**。类型之所以不需要一个旁路的静态分析,是因为它退化成 pair 里的一个槽,由运行时统一去处理。那么,"属性"只要也占据 pair 的另一个槽,**就自动继承了同一套统一 / 惰性 / 组合 / 检查机制**。这正是本报告的核心论断:

> **属性不是第二套类型系统;它是同一个 pair / 统一机制里,与类型并列的另一个槽。**

---

## 2. 核心抽象: schema 是编译期类型,属性是 pair 的另一个槽

lichen 的普通"类型"是**运行时值**(pair 的槽 1),而 **schema 是编译期(静态)类型** —— lichen 第一个真正的静态事物。schema 描述一个表达式运行时 pair 的**形状**:几元、哪个属性在哪个槽。它在 lowering 时被消费,然后消失;**从不成为运行时节点、从不被统一、从不被克隆**。

```
Schema<A> { tail: Vec<A> }
```

- `tail = []` —— 普通 2 元 pair `[value, type]`;
- `tail = [Perspective]` —— 3 元 pair `[value, type, attr]`。

`e # p` 把这个表达式从 2 元变成 3 元。**没有固定元数**:是 2 元还是 3 元完全由 schema 在 lowering 时逐表达式决定。在每一个统一位置,检查器用扩展的 `missing_value()` 补齐缺席的属性,使两侧等长、槽位对齐,然后低层的**定位统一**直接可用 —— 这与类型槽的处理方式一模一样。

属性值是**运行时值**(Perspective → `USize`),像类型一样参与统一。于是"属性"和"类型"在结构上是同一类东西:一个 pair 槽、一个 runtime value、一个 lattice、在同一个检查点被统一。

---

## 3. 属性自己的"类型系统": 一个整除格

Perspective 的取值是一个非负整数 `n`,意思是"在 **n** 个对齐线程上均匀"。它的序是**整除**,不是数值大小:

| 量                          | 值               | 角色                                                  |
| --------------------------- | ---------------- | ----------------------------------------------------- |
| 子类型序                    | `a ⊑ b ⟺ a \| b` | `2⊑4`,`2⊑6`,`4⊑12`;`4` 与 `6` 不可比                  |
| **meet**(最大公共子类型)    | `gcd`            | `gcd(4,6)=2` —— 组合规则                              |
| join(最小公共超类型)        | `lcm`            | `lcm(4,6)=12` —— 阶段 2 未用                          |
| **top**("在全部线程上均匀") | `0`              | 对任意 `n` 有 `n \| 0`;使 `gcd(n,0)=n` 成为 meet 恒等 |
| **bottom**("最细")          | `1`              | `1` 整除一切                                          |

两个容易踩的坑(两者都在设计时导致过回退):

- **序是整除,不是 `≤`**。`2` 数值上小于 `4`,却是一个**子类型**。
- **`0` 是顶,编码为 `0`(不是 `∞`)。** 因为我们没有"无限线程"这种整数:`0` 作为**整除恒等**存在,`gcd(n,0)=n`。而**缺失(missing)**在 GPU 代码里就是"不按线程表示"——所以它**恰好就是"在全部线程上均匀"**,即顶。Rust 整数没有 `∞`,于是顶折入 `0`。

> 这一点的语义后果(后面的子类型行为都由此而来):一个没有 `#` 注解的值,不是"没有属性",而是"在全部线程上均匀"—— 即**顶**。

## 4. 让属性像类型一样: 可插拔的 `AttrExt`

高层 checker 是**属性无关**的:它只认识"一个属性在子表达式上做什么"(meet 组合、缺席取缺失、两个槽按某规则统一),从不知道"perspective = gcd, missing = 0"。它通过 `schema.tail` 的标记向 registry 要 `AttrExt`:

```rust
pub trait AttrExt<P: HighProgram> {
    fn slot(&self) -> usize;                        // 属性占据的槽(第 1 个属性 → 2)
    fn missing_value(&self) -> LowValue;            // 缺席读数(perspective → 0 = 顶)
    fn combine(&self, checker, children) -> NodeId; // 子表达式属性的 meet(→ Gcd)
    fn unify_slots(&self, checker, a, b, span);     // 两个槽的统一
    fn is_subtype(&self, checker, sub, super) -> bool; // 可选子类型放宽(默认 false)
}
```

- **`slot`** 决定属性在 `[value, type]` 头之下占据哪个位置 → 第 1 个属性是槽 2。
- **`missing_value`** 是缺席时读到的值(Perspective → `0`,在 `gcd` 中中性、在相等统一中具体)。
- **`combine`** 把子表达式的属性槽合成一个节点:Perspective → 一个 n 元 `Gcd`。缺席子节点读 `0`(被检查器补上),所以 `(1 # 4 + 2) # 4` 推导 `gcd(4,0)=4`。
- **`unify_slots`** 统一两个槽:Perspective → 相等统一 + 子类型放宽(见 §5)。
- **`is_subtype`** 是有待触发的扩展点(默认 `false`,即严格相等)。

`Gcd` 是**语言层的操作符**(`GcdOp::Gcd`,作为 `LangOperator` 的一个成员),通过 `enum_ext!` 与 `LowOperator`/`TypeOperator` 平铺。低层核心**从不命名它** —— 这与类型侧的 `TypeOperator` 一样,都是"核心只提供机制,具体语义在扩展里"。

`Perspective` 的全部语义(`missing = 0`、`combine = gcd`、`unify = 相等+子类型`)都只出现在 `lichen-language`。

## 5. 与类型"同一方式" —— 对照

把属性系统与 lichen 已有的类型机制并排,它们的每一层都是同构的:

| 方面          | 类型(type)                     | 属性(attribute)                       |
| ------------- | ------------------------------ | ------------------------------------- |
| 承载          | pair 槽 1(运行时值)            | pair 槽 2(运行时值 `USize`)           |
| 形状/静态信息 | 由语法决定,无 schema           | 由 **schema**(`tail`)决定             |
| 元数          | pair 固定 2 元                 | 由 schema 决定 2 元或 3 元            |
| 可选性        | `: T` 可选注解                 | `# p` 可选注解                        |
| 缺席          | 无注解 → 正常类型              | 无注解 → `missing_value()` = `0`(顶)  |
| 统一          | 同一 unify                     | 同一 unify(定位、等长、slot 对齐)     |
| 组合          | 由构造决定(函数类型/元组类型…) | 子表达式属性的 meet(`gcd`)            |
| 约束点        | 注解、二元 `Int` 检查、apply   | 注解、`# p`、apply 处的 `unify_slots` |
| 检查即运行    | 运行时统一                     | 运行时统一(同一低层 apply)            |
| 与核心的解耦  | `P::Value` + `ValueType`       | `P::Attr` + `AttrSpec` + `AttrExt`    |

要点:类型"是"一个值,所以它不需要旁路静态分析;属性**也是**一个值(占另一个槽),所以它也**不需要**旁路的静态分析。两者共用**同一个** pair、**同一个** unify、**同一个** apply 检查点、**同一个**惰性求值。属性的"格"(整除)、"组合"(gcd)、"缺失"(0)、"子类型"(整除)只是 `AttrExt` 提供的**语义**,不是核心里的特殊分支。

## 6. 子类型放宽: 检查即统一的一般化

类型侧的 lichen 统一目前是**相等**(两个值一致才合一)。属性系统把它推进了一步:允许属性注册一个可选的 `is_subtype`,在相等统一失败后**重查是否满足子类型,满足则抑制错误**。

```rust
// checker 新入口: 尝试统一,失败则重查 is_subtype
pub fn check_unify_relaxed(&mut self, a, b, span, kind, is_subtype: impl Fn(&Checker, NodeId, NodeId) -> bool) {
    let before = self.module.unify_errors.len();
    self.module.unify(a, b);
    if self.module.unify_errors.len() > before {
        if is_subtype(self, a, b) {
            self.module.unify_errors.truncate(before);   // 满足子类型 → 抑制
        } else {
            // 记录诊断(Attribute kind)
        }
    }
}
```

Perspective 覆写 `is_subtype`(默认 `false` = 严格相等,完全向后兼容):

```rust
fn divides(sub, sup) = if sub == 0 { sup == 0 } else { sup % sub == 0 }
```

方向(来自论文 §3.6):perspective `n` = "在 n 个对齐线程上均匀",那么一个值在 `q` 被声明时可用,当且仅当 `q | n`(对齐的 n 组可划分成 q 组,故 uniform-n ⟹ uniform-q)。也就是 **`declared ⊑ argument`(`declared | argument`)**。

`0` 是顶("在全部线程上均匀"):只有 `0` 满足"在全部线程上均匀"的要求;而一个 `0`(全局均匀)值满足任何 `# n` 要求。于是 `divides` 的三个分支在语义上是自洽的:

- `divides(0, sup) ⟺ sup == 0`: 一个 `# 4` 值不满足"全局均匀"(`id (5 # 4)` 报错);
- `divides(n, 0) ∈ true`(因为 `0 % n == 0`): 一个"全局均匀"值满足 `# 4` 要求(`f = x # 4 => x; f 5` 通过);
- `divides(n, m) ⟺ m % n == 0`: 真正的子类型(`f = x # 2 => x; f (5 # 4)` 因 `2|4` 通过,而 `f = x # 4 => x; f (5 # 2)` 因 `4∤2` 报错)。

### 行为表

| 程序                        | 结果                                              |
| --------------------------- | ------------------------------------------------- |
| `1 # 4`                     | perspective `4`                                   |
| `((1 # 4) + (2 # 6)) # 2`   | 槽 = `gcd(4,6) = 2`,检查 `2 ≡ 2` ✓                |
| `((1 # 4) + (2 # 6)) # 5`   | `2 ≢ 5` ✗(“expected 5, found 2”)                  |
| `((1 # 4) + 2) # 4`         | `gcd(4,0) = 4` ✓(缺席子节点读 0)                  |
| `id 5`(`id = x => x`)       | 参数读 `0`,实参 `0` → `0 ≡ 0` ✓                   |
| `id (5 # 4)`                | `0 ≢ 4` ✗ —— 一个 `# 4` 值不满足"全局均匀"(顶)    |
| `f = x # 4 => x; f (5 # 4)` | `4 ≡ 4` ✓                                         |
| `f = x # 4 => x; f 5`       | `4 \| 0` ✓ —— 一个"全局均匀"(顶)值满足 `# 4` 要求 |
| `f = x # 2 => x; f (5 # 4)` | `2 \| 4` ✓ —— 真正子类型放宽                      |
| `f = x # 4 => x; f (5 # 2)` | `4 ∤ 2` ✗                                         |
| `g = x => (x # 4); g 5`     | apply `0≡0` ✓，返回 `5 # 4`                       |

这其实是"检查即统一"的**一般化**:统一不再只是相等,而是"相等或满足所注册的偏序"。类型侧目前是相等,但这一般化能力是属性系统引入的——将来类型侧也完全可以注册自己的偏序。

## 7. 意义与展望

这个设计最有价值的地方,是它**没有引入第二套类型系统**。它只是让"属性"也成为一个 pair 槽、一个运行时值、一个带格序的东西,然后复用 lichen 已有的"类型即值",把 `AttrExt` 的语义注入进去。于是:

- 高层核心保持**属性无关**,只依赖 `AttrExt` 的形状;
- 具体语义(格、组合、缺失、统一、子类型)都在语言扩展里;
- `Schema::tail` 是 `Vec<Attr>`,**第二个属性**会自然落地;
- 一个 GPU DSL 前端、生命周期、效应、或 staging 级别,都能以同样的方式接入;
- **子类型放宽**是"检查即统一"的一般化能力,类型侧将来也可借用。函数\*\*(自动推导,目前 apply 只"检查"不"传播")、解查函数值的 code perspective,以及接入一个真正的 GPU DSL 前端。
