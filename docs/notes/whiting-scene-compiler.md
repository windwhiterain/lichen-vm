# A lichen program as a whiting scene: the `LichenSceneCompiler`

> Status: **proposed.** Nothing here is implemented. This is the shape of an
> integration and the list of obstacles it has to clear, not a description of
> what the code does today.
>
> **Decided**, and not to be re-opened without a new reason: the shape is a
> `scene::Compiler` implementation whose scene is the value of a lichen program,
> **not** a native plugin; the device is **not** part of the first phase; and a
> float is added to the lowlevel rather than worked around
> ([floating-point](floating-point.md)).
>
> Points at, on this side: `crates/lichen-language/src/session.rs`
> (`BufferSession`, `SessionReport`, `CellEvents`),
> `crates/lichen-language/src/lib.rs` (`compile_with_cells`),
> `crates/lichen-language-parser/src/path.rs` (`Step`, `Path`, `children`,
> `resolve`), `crates/lichen-render/src/render.rs` (`struct_field_names`),
> `crates/lichen-lowlevel/src/lib.rs` (`LowValue`, the arena handles).
> On the other side, in `C:\resource\whiting`: `crates/scene/src/lib.rs`
> (`Compiler`, `CompileContext`, `CompileOutput`, `assemble`),
> `crates/scene/src/diff.rs` (`document_delta`), `crates/definition/src`
> (`Value`, `Schema`, `Delta`, `Path`), `crates/device/src/state.rs`
> (`Device::reload`).
> The incremental mechanism this depends on is
> [incremental-update](incremental-update.md); the plugin rule it must be argued
> against is [plugin-taxonomy](plugin-taxonomy.md).

## 1. The two sides, as shapes

**whiting** is document-driven and CPU-light where it matters. A scene is a
`.ron`-shaped `Value` validated against a `Schema` that is itself a document; a
`Compiler` turns it into a graphics document and an instance document and emits,
alongside both, the `Delta` that reaches them from the previous pair. The
compilers are `ReferenceScene` and `StandardScene` — note there is no
`StandardCompiler`; `StandardScene` is the compiler *type*. `definition`,
`graphics` and `scene` depend on `facet` and `thiserror` and nothing else: no
wgpu, no tokio, no axum, and no `unsafe` anywhere in the workspace. `device` is
the only crate that touches a GPU, and it is the only one that would be expensive
to link.

**lichen** is code-driven and has an incrementality mechanism that whiting does
not: identity is a node's **occurrence path** from the program root, retention is
a `cache` mark the author wrote, and reuse is decided by **dirty propagation** —
never by a content key, a hash, or any identity derived from a value. A host
drives it with one `BufferSession` per open document and reads a `SessionReport`
whose `CellEvents { reused, frozen, dropped }` says what the compile did.

The two path vocabularies are nearly the same shape: lichen's
`Step::{Name, Index, Tail}` against whiting's `PathSegment::{Key, Index}`. That
similarity is suggestive and is **not** load-bearing here; §5 is about what is
actually shared, and the honest answer is the dirty set, not the path type.

## 2. What is actually missing, and it is not what it looks like

whiting has a delta, a version, a history, and a per-binding GPU resource
contract. It does **not** have an incremental compiler. `StandardScene::compile`
re-reads the whole scene and re-emits both documents from scratch on every call;
`emit` takes no previous document, and `scene::assemble` diffs the two freshly
built documents afterwards. The delta is therefore **transport, plus history and
undo** — it says what changed and it applies atomically, but nothing is skipped
in the finding.

whiting has measured this to the millisecond, in
`C:\resource\whiting\.agents\proposals\compile-cost.md`, and the numbers are the
reason this integration is worth doing at all. Over a dune field of 55,296
points, per frame: **21–32 ms of render against 1.7–3.7 s of compile**, and the
document's own conclusion is that the delta "makes applying a change cheap, and
finding the change expensive". Three fixes in that document brought the compile
to 10 ms — packing the point runs so the diff is a `memcmp`, and two redundant
walks removed — and its closing line is:

> Ten milliseconds of render against ten of compile. The number to beat is the
> render.

**That is the hole.** Not the delta, not the renderer, not the format: the work
of re-deriving content that did not change. And that is precisely what a lichen
`cache` cell is for.

A lichen-authored scene inverts the layering. In whiting's own scenes the
geometry is *generated by Rust* — `gallery::geometry` builds a heightfield and
packs it — so changing a scene means a `cargo build`, and the generation cost is
outside anything the framework measures. Put the generation in the program
instead and the framework can see it: an agent edits one number, lichen's dirty
propagation re-derives the one `cache` cell whose inputs moved, the scene
document's untouched slots come back as the same packed run, `document_delta`
compares it with a `memcmp` and finds nothing, and no operation is emitted for
it.

So the claim this integration makes is narrow and checkable:

> **The scene program's re-derivation becomes incremental; the emitted delta was
> already correct and stays correct, because it is computed from whatever the
> program produced.**

It is a claim about *finding* a change, not about applying one. It does not make
`document_delta` faster — that is already a `memcmp` — and it does not make the
frame faster.

## 3. The shape

```rust
// An out-of-tree scene::Compiler whose CompileContext is not the only input.
impl scene::Compiler for LichenSceneCompiler { … }
```

`CompileContext` already carries everything a compile needs from whiting's side:
the scene `Definition`, the previous graphics and instance `Definition`s, the
`Registry`, a camera index and the device's `DeviceLimits`. The one thing it does
not carry is the program, which is the compiler's own field — the same shape as
`StandardScene`'s `debug` channels, which are a field of the compiler rather than
an argument of `compile` because the device's cross-check recompiles with the
compiler it holds.

The compile is then:

1. re-evaluate the program (or read the cells a dirty compile did not reach),
2. convert the resulting value to a `definition::Value` (§5),
3. validate it against `scene_schema()`,
4. hand it to the existing compiler and let **it** emit graphics, instance and
   their deltas — or emit them here, if §6's first obstacle forces this,
5. return `CompileOutput { graphics, instance, graphics_delta, instance_delta, notes }`.

Step 4 is the reason the shape is worth taking rather than a re-implementation:
whiting's emitter, its binder derivation, its vertex-layout rules and its WGSL
interface check are the part that is hard to get right and there is no reason to
write a second copy of them.

## 4. Where the device goes, and why not in phase one

The device is the only crate that drags `wgpu` 30, `axum` and `tokio` in, and
this workspace's stated discipline is the opposite: `lichen-compute-gpu`'s own
manifest says that a build which never dispatches a kernel to a device must never
link a GPU loader, and the stock `lichen-compiler` binary accordingly cannot
reach one — `install_default` is called only from tests.

So when a device is added it goes **out of process**, over the RPC whiting
already serves (`POST /reload/{name}`, `POST /render/{name}`,
`POST /render/{name}/png`), and lichen links `scene` only. That is also
whiting's own deployment story, so nothing has to be built for it.

Phase one has no device at all. That is a deliberate gate: it tests the only part
that is genuinely uncertain — the conversion in §5 — against nothing that could
hide a failure behind a picture.

## 5. The conversion

One function, `lichen value → definition::Value`, and it is where every real
difficulty of this integration lives. The rules are short; the two rules that are
not obvious are called out because they are the ones that will be got wrong.

| a lichen | becomes | note |
|---|---|---|
| `LowValue::USize` | `Value::Int` | |
| `LowValue::Float` | `Value::Float` | blocked on [floating-point](floating-point.md) |
| `LowValue::Str` | `Value::String` | atomic on both sides; no escapes either way |
| `LowValue::Array` | `Value::List`, or `Value::Packed` | see below |
| `LowValue::Table` | `Value::Dict` | |
| a struct value | `Value::Struct` | **field names come from the type chain** |
| a type marker | `Value::Enum { tag, … }` | |

**Struct field names come from the type, not the value.** A lichen struct's value
is positional; its names live in the kind marker's slot 0, `[TypeStruct{id, names},
K]`, where `names` is a `table` of `string → index`. `lichen-render` already
reads this — `struct_field_names` in `crates/lichen-render/src/render.rs` is the
reference implementation, and `render_struct_fields_named` is its public face. A
conversion that reads field names off the value will produce a document no
schema admits, which is the cheapest possible failure.

**An array becomes a packed run whenever the schema can guarantee one
structure.** `Value::Packed` is the same kind as `List` and a schema accepts
either, so packing is a representation and never a change of meaning — and it is
what makes §2's arithmetic work at all: the diff of a packed run is a `memcmp`,
and the validation of one is `len % stride == 0` instead of a walk per point. A
conversion that always emits `List` would be correct and would throw away the
entire reason this integration is cheap.

Two things have no counterpart and are worth stating plainly rather than
discovering later: whiting's `Value::Bytes` has nowhere to land in `LowValue`,
and a scene that carries a shader's WGSL source carries several kilobytes of
`&'static str`, which is exactly as atomic on this side as it is there.

The conversion walks arena handles, so it is `unsafe` in the way
`SortOp::run` is (`lichen-std-native` is the worked example of reading a nested
lichen value from Rust). That is the only unsafe the integration adds; whiting
has none.

## 6. The obstacles, named

**`scene::assemble` is `pub(crate)`.** The function that stamps the instance's
`REFERENCING_GRAPHICS`, validates both emitted documents and builds the two
deltas from `document_delta` is crate-private, so an out-of-tree compiler builds
`CompileOutput` itself from public fields. `CompileError::GraphicsDeltaMismatch`
and `InstanceDeltaMismatch` exist for a compiler's own check, which suggests this
was anticipated. **This is the first thing to settle**, because it decides
whether `LichenSceneCompiler` wraps `StandardScene` or replaces it.

**The float.** Decided: added to the lowlevel, not worked around. See
[floating-point](floating-point.md); the conversion above cannot be written
without it, and §2's arithmetic cannot be shown without it.

**`Loaded` is single-threaded.** `Loaded`, `Store` and `RegistryStore` are
`Rc`-based; `Registry`, `Value`, `Schema`, `Delta` and both compilers are not.
A compile resolves the scene through `RegistryStore`, so **one compile at a
time** — which is also what `Device`'s single mutex already enforces.

**A delta that crosses a reference is a different mutation path.** `Registry::apply`
refuses a path that crosses one; `Loaded::patch` is the path that handles it. A
scene that names a mesh defined elsewhere lands in that case, and the scene
schema's `meshes` slot *is* a reference slot — so this is the expected case, not
an edge one.

**whiting is mid-flight and unversioned.** No tags, no published crates, ten
modified files and nine untracked entries on `main`, four live handoffs, and
three feature branches whose worktrees carry **duplicate crate trees inside the
repository** — which will confuse any tooling that walks the tree, including a
line count. A git dependency pins nothing useful until there is a tag, so
development needs a local patch, on the model of the
`[patch."https://github.com/windwhiterain/lichen-vm"]` block the root manifest
already keeps. Both repositories are under one account, so a git dependency is
available at all.

**Nothing on the GPU is cached across renders.** Pipelines, bind groups, buffers
and textures are built per render; only shader modules and their parsed forms
survive, keyed by source text. So "hot reload is fast" is a statement about the
compile and the delta, never about the frame, and an integration that claims
otherwise would be claiming a cache that does not exist.

## 7. Phase one, and how it is verified

The deliverable is deliberately small: a `.lichen` scene program compiles into a
validated scene `Value`, `StandardScene::compile` accepts it, and the emitted
delta's operation count is **O(1) in the size of the document** for a one-field
edit. No GPU, no device, no wgpu, no RPC.

That claim is checkable without a picture, which is the point of doing it this
way: the assertion is on the operation count and on a byte-identical result for
the unchanged slots, not on "the render looks right". A probe that lies — because
the render did not re-run, or because the document did not change — is the single
most expensive failure mode recorded in whiting's own
`.agents/proposals/agent-scene-iteration-loop.md`, where three independent agent
runs lost the most time to exactly that, and the framework had the answer (an
empty delta) and did not print it.

The dependency set for this phase is `whiting-definition`, `whiting-graphics` and
`whiting-scene`, which is `facet` and `thiserror` — a light enough addition that
the phase does not have to argue about the GPU-loader discipline at all.

## 8. Not decided

Whether a mesh becomes its own whiting definition shared by several scenes (the
second route whiting's own proposal names, and one a lichen `import` maps onto
directly) is **not** decided here; it is orthogonal to the phase-one gate and
should be argued on its own evidence.

The `Compiler`/`Assemble` question in §6 must be settled first, and the
operator/kernel questions in [floating-point](floating-point.md) must be settled
before the lexer moves.

## 9. Rejected

**A native plugin** (`NativePlugin` + leaves + `NativeOp` + `OperatorExt` + an
embedded wrapper) is the cheaper integration and it is what
[plugin-taxonomy](plugin-taxonomy.md) would classify this as if the scene were
opaque. It was rejected because it yields a program that *drives* a device, not a
program that *is* a scene: the scene's numbers would still have to be born
somewhere other than a lichen expression, and §2's incrementality would not
exist. If the float is never added, this note's decision is the wrong one and the
native plugin is the right answer — the two are not independent.

**Porting the delta algebra into lichen** — `Definition`, `Path`,
`PrimitiveDelta` and `History` as lichen values and operators — fits the
project's thesis unusually well, and was rejected only because it exposes the
whole of `definition` to answer a question the integration does not ask. It is
the right shape for a *different* goal: letting the editing loop itself be a
program.

**Not integrating, and driving whiting over its existing RPC**, costs nothing and
is already how the framework is meant to be driven by an agent. It is the
fallback if phase one shows the conversion is not worth its cost, and saying so
now is cheaper than discovering it in a month.
