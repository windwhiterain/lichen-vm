# A lichen program as a whiting scene: the seam is a document

> Status: **proposed.** Nothing here is implemented. This is the shape of an
> integration and the list of obstacles it has to clear, not a description of
> what the code does today.
>
> **Decided**, and not to be re-opened without a new reason: lichen's whole
> contribution is **one `definition::Value`** — the scene document — and nothing
> more. No `scene::Compiler` implementation, no `CompileOutput`, no device in
> the first phase, and a float added to the lowlevel rather than worked around
> ([floating-point](floating-point.md)). The document is **written to disk** and
> whiting reads it, so this side links `whiting-definition` and no GPU loader.
>
> Points at, on this side: `crates/lichen-language/src/session.rs`
> (`BufferSession`, `SessionReport`, `CellEvents`),
> `crates/lichen-language/src/lib.rs` (`compile_with_cells`),
> `crates/lichen-render/src/render.rs` (`struct_field_names`),
> `crates/lichen-lowlevel/src/lib.rs` (`LowValue`, the arena handles),
> `crates/lichen-highlevel/src/checker.rs` (`Build`).
> On the other side, in `C:\resource\whiting`: `crates/definition/src`
> (`Value`, `Schema`, `Definition`, `Reference`), `crates/device/src/lib.rs`
> (the insert-reload-render doctest), `crates/device/src/rpc.rs`,
> `crates/device/src/snapshot.rs`, `crates/scene/src/standard/compiler.rs`
> (`StandardScene`), `crates/scene/src/diff.rs` (`document_delta`).
> The incremental mechanism this depends on is
> [incremental-update](incremental-update.md); the plugin rule it must be argued
> against is [plugin-taxonomy](plugin-taxonomy.md).

## 1. The two sides, as shapes

**whiting** is document-driven and CPU-light where it matters. A scene is a
`.ron`-shaped `Value` validated against a `Schema` that is itself a document;
whiting's own `StandardScene` turns that into a graphics document and an instance
document and emits, alongside both, the `Delta` that reaches them from the
previous pair. `definition`, `graphics` and `scene` depend on `facet` and
`thiserror` and nothing else: no wgpu, no tokio, no axum, and no `unsafe` anywhere
in the workspace. `device` is the only crate that touches a GPU, and it is the
only one expensive to link.

The seam whiting already offers is short enough to quote: install the graphics
schemas, register the scene schema, `insert_definition` a scene `Definition`,
`reload` it, `render` the graphics. That is the flow in
`crates/device/src/lib.rs`, and **this integration stops at the first of those
five steps**.

**lichen** is code-driven and has an incrementality mechanism that whiting does
not: identity is a node's **occurrence path** from the program root, retention is
a `cache` mark the author wrote, and reuse is decided by **dirty propagation** —
never by a content key, a hash, or any identity derived from a value. A host
drives it with one `BufferSession` per open document and reads a `SessionReport`
whose `CellEvents { reused, frozen, dropped }` says what the compile did.

## 2. What is actually missing, and it is not what it looks like

whiting has a delta, a version, a history, and a per-binding GPU resource
contract. It does **not** have an incremental compiler. `StandardScene::compile`
re-reads the whole scene and re-emits both documents from scratch on every call;
`emit` takes no previous document, and the scene crate diffs the two freshly
built documents afterwards. The delta is therefore **transport, plus history and
undo** — it says what changed and applies atomically, but nothing is skipped in
the finding.

whiting has measured this to the millisecond, in
`C:\resource\whiting\.agents\proposals\compile-cost.md`, and the numbers are the
reason this integration is worth doing at all. Over a dune field of 55,296
points, per frame: **21–32 ms of render against 1.7–3.7 s of compile**, and the
document's own conclusion is that the delta "makes applying a change cheap, and
finding the change expensive". Three fixes in that document brought the compile
to 10 ms — packing the point runs so the diff is a `memcmp`, and two redundant
walks removed — and its closing line is:

> Ten milliseconds of render against ten of compile. The number to beat is the
> render.

**That is the hole.** Not the delta, not the renderer, not the format: the work of
re-deriving content that did not change. And that is precisely what a lichen
`cache` cell is for.

A lichen-authored scene inverts the layering. In whiting's own scenes the geometry
is *generated by Rust* — `gallery::geometry` builds a heightfield and packs it —
so changing a scene means a `cargo build`, and the generation cost sits outside
anything the framework measures or can cache. Put the generation in the program
instead and it comes back inside the measurement: an agent edits one number,
lichen's dirty propagation re-derives the one `cache` cell whose inputs moved,
that cell's value comes back **the same value**, and the document's untouched
slots come back as the same packed run — so `document_delta` compares them with a
`memcmp`, finds nothing, and emits no operation for them.

**What this saves, stated exactly:** producing the document becomes incremental.
It does **not** make whiting's compile incremental — the handoff is a whole
document, so `reload` still re-emits and diffs in full every time, and that cost
is whiting's ten milliseconds. A note that claimed otherwise would be claiming a
compiler that does not exist, which is the mistake §3 records.

## 3. The seam

```text
scene.lichen ──compile & evaluate──▶ lichen value
                                       │
                                       │  §5 conversion
                                       ▼
                            definition::Value  ── write ──▶ scene.json
                                                                     │
                          whiting reads it:  reload → render       ▼
```

One function in, one document out. There is no trait to implement, no
`CompileContext` to supply, and no `CompileOutput` to assemble.

**Why there is no `Compiler` here, since the obvious next question is why not.**
An earlier draft of this note proposed a `LichenSceneCompiler: scene::Compiler`,
on the reasoning that whiting exposes a compiler trait and lichen should fill it
in. That reasoning was wrong in a way worth recording. `CompileContext` carries
`previous_graphics` and `previous_instance`, which looked like an incremental
interface — but whiting's own `StandardScene` does not use them either, because
`emit` takes no previous document (§2). The trait is the shape a *future*
incremental compiler would have, and implementing it would have bought nothing
while costing three real things: `scene::assemble` is `pub(crate)`, so an
out-of-tree compiler must rebuild `CompileOutput` by hand; `Loaded` is `Rc`-based,
so the compile is single-threaded; and a delta whose path crosses a reference has
to go through `Loaded::patch` rather than `Registry::apply`. All three are
someone else's problem the moment the seam is a document.

There is one case where the trait would earn its place: sending lichen's dirty
set to whiting **as a delta**, so the scene is patched rather than replaced.
`Device::reload` recompiles either way, so it buys nothing today. If it is ever
wanted it is a change to whiting's device, not to this seam.

## 4. Where the document goes

Two ways to hand one over, and the decision is the second.

**In process.** `Definition::new(identifier, schema_identifier, value)` then
`registry.insert_definition`. Simplest, and it costs the GPU-loader discipline
this workspace keeps on purpose: `whiting-device` drags in `wgpu` 30, `axum` and
`tokio`, while `lichen-compute-gpu`'s own manifest says a build that never
dispatches a kernel to a device must never link a GPU loader — a discipline the
stock `lichen-compiler` currently honours, because `install_default` is called
only from tests.

**On disk.** lichen writes the document; whiting's own harness, or a client of its
RPC, reads it. This keeps the dependency at `whiting-definition` plus whatever
serialises it, and it is not a compromise: a document on disk is **diffable**,
which is the diagnostic whiting's own
`.agents/proposals/agent-scene-iteration-loop.md` says was the most expensive
gap in three independent agent runs — "I changed something and the picture did
not move". A written document turns that from a ten-minute bisect into a `git
diff`.

So: **the document is written, not inserted.**

## 5. The conversion

The conversion is one function, `lichen value → definition::Value`, and it is
where every real difficulty lives. The rules are short; the two that are not
obvious are called out because they are the ones that will be got wrong.

| a lichen | becomes | note |
|---|---|---|
| `LowValue::USize` | `Value::Int` | |
| `LowValue::Float` | `Value::Float` | blocked on [floating-point](floating-point.md) |
| `LowValue::Str` | `Value::String` | atomic on both sides; no escapes either way |
| `LowValue::Array` | `Value::List`, or `Value::Packed` | see below |
| `LowValue::Table` | `Value::Dict` | |
| a struct value | `Value::Struct` | **field names come from the type chain** |
| a type marker | `Value::Enum { tag, … }` | |

**Struct field names come from the type, not the value.** A lichen struct's value
is positional; its names live in the kind marker's payload — `[payload,
TypeStruct]` under the kind's `[marker, K]` pair, with `payload = [TypeId, names,
names_in_order]` — where `names` is a `table` of `string → index`. `lichen-render` already reads
this — `struct_field_names` in `crates/lichen-render/src/render.rs` is the
reference implementation, and `render_struct_fields_named` is its public face. A
conversion that reads field names off the value produces a document no schema
admits, which is the cheapest possible failure.

**An array becomes a packed run whenever the schema can guarantee one structure.**
`Value::Packed` is the same kind as `List` and a schema accepts either, so packing
is a representation and never a change of meaning — and it is what makes §2's
arithmetic work: the diff of a packed run is a `memcmp`, and validating one is
`len % stride == 0` rather than a walk per point. A conversion that always emits
`List` would be correct and would throw away the entire reason this is cheap.

Two things have no counterpart and are worth stating rather than discovering: a
`Value::Bytes` has nowhere to land in `LowValue`, and a scene carries each
shader's WGSL source as several kilobytes of `&'static str`, which is exactly as
atomic on this side as it is there.

The conversion walks arena handles, so it is `unsafe` in the way `SortOp::run`
is — `lichen-std-native` is the worked example of reading a nested lichen value
from Rust. That is the only unsafe the integration adds; whiting has none.

**The text format has now been measured, and it is the constraint that decides
how this integration is shaped.** §4's handoff assumed a document lichen writes
and whiting reads. That much holds: `PUT /definition/{name}` takes
`{ schema, value }`, `POST /reload/{name}` compiles it, and
`POST /render/{name}/png` returns the frame, so **phase one needs no new whiting
code on the read side**. What a probe established — see §6 — is that the encoding
is workable for a document and **not workable for a mesh**.

Two things follow for this side. The writer is version-coupled, so **pin
`facet`/`facet-core` to `0.45.0` and `facet-json` to `0.44.7` deliberately**,
and depend on `whiting-definition` rather than re-spelling `Value` in lichen —
the text is produced by `facet-json`, not by the type, so a copy of the enum
drifts silently. And the round trip is not universal, so a writer here is a
writer of a format with **named, silent failure modes** (§6).

## 6. The obstacles, named

**The float.** Decided: added to the lowlevel, not worked around. See
[floating-point](floating-point.md). The conversion in §5 cannot be written
without it, and §2's arithmetic cannot be shown without it. This is the critical
path.

**A packed run cannot go through the text format.** This is the finding that
reshapes the handoff, and it is measured rather than estimated. `PackedList`
derives `Facet` as a struct of `layout` plus `Vec<u8>`, and `facet-json` writes a
`Vec<u8>` as a JSON array of decimal `0`–`255`. For a 20,000-point mesh at a
24-byte stride:

| | bytes | factor | time |
|---|---|---|---|
| the run itself | 480,000 | — | — |
| `to_string` | 1,262,205 | ×2.63 | 63.5 ms |
| `to_string_pretty` | 1,262,325 | ×2.63 | 64.2 ms |
| `from_str` | 1,262,205 | ×2.63 | **599.5 ms** |
| the same data expanded as a `Value::List` | 2,746,680 | ×5.72 | — |

A 100,000-point mesh is ≈2.4 MB of run, ≈6 MB of JSON, and ≈3 s of parsing — per
mesh, on every read and every write. `Bytes` behaves identically, and
`to_string_pretty` does not indent the byte array, so there is no pretty form to
fall back on.

There is a compact spelling in the library —
`SerializeOptions::default().bytes_as_hex()` writes `{"Bytes":"0x00017fff"}` —
and **the default reader cannot read it back**, so it is write-only and unusable
for any route the device must accept. There is no base64.

**Consequence for this design: phase one ships no mesh, and that is the honest
scope.** A scene of lights, materials, cameras and shaders is a few kilobytes and
round-trips fine; a mesh is not. Three ways out exist and none of them is a
lichen-side decision:

- **A binary sidecar.** whiting's `Reference::File` already resolves a slot to
  bytes or to a nested document, so the run could be named rather than spelled.
  It needs a custom `Store` — `RegistryStore::file` always errors by design — so
  it is whiting-side work, small and in the right place.
- **A mesh as its own definition.** whiting's own proposal names this route:
  `meshes` is already a reference slot, so a mesh can live in a definition of its
  own and be named by any number of scenes. It solves the *re-derivation* half and
  **not** the byte count.
- **A bytes format that is not decimal.** This is the actual fix, and it belongs
  to whiting: make the hex form readable, or add base64. Until one of those
  lands, no amount of care on this side makes a large mesh cheap.

**The float round trip is not universal, and three of its failures are silent.**
Measured on the same facet-json: `-0.0` writes as `-0` and reads back `+0.0`; any
`f64` whose shortest form is a bare integer of 40 or more digits — that is
`|x| ≥ 1e39`, which includes `f64::MAX` — **fails to parse**; and `NaN` and `±inf`
write as `null` and read back as `0.0` **with no error at all**.

The last one is the dangerous one, and it meets
[floating-point](floating-point.md) §4.3 directly: that decision lets the lexer
produce an infinity, and an infinity in a scene document now loads as `0.0`. A
document format that turns a value into a different value without complaining is
the failure class §4.3's invariant is written against.

`Unit` is the bare JSON string `"Unit"` while every other variant is an object,
so a guessed encoding is wrong; `Enum` is a two-field struct variant, so it
encodes as `{"Enum": {"tag": …, "fields": {…}}}` rather than as a tagged union.

**A reference is not a value.** whiting's reference slots are marked by the
schema and resolved at load; a scene that names a mesh defined in another
document depends on that resolution and a hand-built `Value` does not carry the
spelling. Whether the first scenes need cross-document references at all is a
question for §8.

**whiting is mid-flight and unversioned.** No tags, no published crates, ten
modified files and nine untracked entries on `main`, four live handoffs, and
three feature branches whose worktrees carry **duplicate crate trees inside the
repository** — which will confuse any tooling that walks the tree, including a
line count. A git dependency pins nothing useful until there is a tag, so
development needs a local patch, on the model of the
`[patch."https://github.com/windwhiterain/lichen-vm"]` block the root manifest
already keeps. Both repositories are under one account, so a git dependency is
available at all.

**Nothing on the GPU is cached across renders.** Pipelines, bind groups, buffers
and textures are built per render; only shader modules and their parsed forms
survive, keyed by source text. So "hot reload is fast" is a statement about the
compile and the delta, never about the frame.

## 7. Phase one, and how it is verified

The deliverable is deliberately small: a `.lichen` scene program compiles into a
validated scene `Value`, the document is written, whiting's own harness reads it
and compiles it, and the reported delta's operation count is **O(1) in the size of
the document** for a one-field edit. No GPU, no device, no wgpu, no RPC.

**Phase one ships no mesh**, and §6 is the reason rather than an omission: a
packed run is six megabytes of decimal and three seconds of parse at a hundred
thousand points, and that number does not improve by anything this side does. A
scene of lights, cameras, materials and shaders is kilobytes and exercises the
whole conversion — including the struct-field-names rule and the `Enum` tag — so
the phase proves what it is meant to prove without a problem it cannot solve. The
mesh path is §8's open question, with real numbers behind it.

That claim is checkable without a picture, which is the point of doing it this
way: the assertion is on the operation count and on the unchanged slots being
byte-identical, not on "the render looks right". A probe that lies — because the
render did not re-run, or because the document did not change — is the single
most expensive failure mode in whiting's agent notes, where the framework had the
answer (an empty delta) and did not print it. `ReloadReport` reports the
operation count, so the answer is available to whoever runs it.

The dependency set for this phase is `whiting-definition` plus `facet-json`,
pinned as §5 says. That is `facet`, `thiserror` and a serialiser — light enough
that the phase does not have to argue about the GPU-loader discipline at all.

## 8. Not decided

Whether a mesh becomes its own whiting definition shared by several scenes — the
second route whiting's own proposal names, and one a lichen `import` maps onto
directly — is **not** decided here. It is orthogonal to the phase-one gate, and
it is the first thing that would make the reference question in §6 bite.

Whether the handoff ever becomes a delta instead of a document is also open, and
belongs to §3's last paragraph rather than to this note.

The operator and kernel questions in [floating-point](floating-point.md) must be
settled before the lexer moves.

## 9. Considered and not taken

**A native plugin** (`NativePlugin` + leaves + `NativeOp` + `OperatorExt` + an
embedded wrapper) is what [plugin-taxonomy](plugin-taxonomy.md) would classify an
external integration as, and `lichen-compute` is the template. It is not needed
here, and it is worth saying why rather than leaving it as an unexamined default:
a plugin is how a program *calls into* a library, and this direction is the
opposite — the program **produces a value** and the library reads it. A host that
compiles lichen already holds `Build<P>` with `module`, `root_val` and `root_ty`,
which is the same data without a vocabulary leaf, a `ValueExt` impl with its
`traced` and `release_obligations` obligations, and a generated compiler. The
plugin machinery buys a call boundary this direction does not want.

**Porting the delta algebra into lichen** — `Definition`, `Path`,
`PrimitiveDelta` and `History` as lichen values and operators — fits the project's
thesis unusually well, and was rejected only because it exposes the whole of
`definition` to answer a question this seam does not ask. It is the right shape
for a *different* goal: letting the editing loop itself be a program.

**Not integrating, and driving whiting over its existing RPC**, costs nothing and
is already how the framework is meant to be driven by an agent. It is the
fallback if the conversion proves not worth its cost, and saying so now is cheaper
than discovering it in a month.
